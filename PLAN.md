# VaultPonyIOS — Plan

VeraCrypt-compatible encrypted vaults on iPhone and iPad, backed by the shared
Rust core (VaultPonyCore), Swift + SwiftUI over the UniFFI boundary. This
document is the source of truth for scope and phasing of the iOS app, the same
way the original planning doc was for the core and Android.

Decisions already made (with Kevin, 2026-08-05): the existing `~/Apps/VaultPony`
directory is wiped and becomes this repo; the GitHub repo is
`norsehorse-dev/VaultPonyIOS`; v1 targets full feature parity with
VaultPonyAndroid; minimum deployment target is iOS 17; the File Provider
extension (vault in the Files app) is deferred to post-v1. License Apache-2.0,
matching VaultPonyCore and VaultPonyAndroid. Not affiliated with or endorsed by
IDRIX; VeraCrypt is a registered trademark of IDRIX — the same notice and
clean-room posture as the sibling repos.

## 1. Shape of the thing

One app target, no extensions in v1. The app consumes VaultPonyCore exactly the
way VaultPonyAndroid does: resolved as a sibling checkout at `../VaultPonyCore`
when present, otherwise the git submodule at `./VaultPonyCore`, overridable via
the `VAULTPONY_CORE` environment variable. The core is never forked or patched
from this repo; anything the iOS app needs from the core (new FFI surface, iOS
Rust targets in `rust-toolchain.toml`) is a change made in VaultPonyCore itself.

The core's fd contract carries over unchanged: the shell opens the container
file however the platform demands and hands the core a dup'd file descriptor it
owns outright. On Android that's SAF and `ParcelFileDescriptor.detachFd()`; on
iOS it's a security-scoped URL from the document picker, `open(2)` on its path,
and the raw fd. The core never sees a path, a URL, or a platform storage API.

Everything user-visible is SwiftUI. State management uses the iOS 17
Observation framework (`@Observable`), not ObservableObject. No third-party
Swift dependencies in v1 — the platform provides everything we need
(SwiftUI, LocalAuthentication, Security/Keychain, UniformTypeIdentifiers,
CryptoKit is not needed since crypto lives in the core).

Why XcodeGen rather than a checked-in `.xcodeproj`: the project file becomes a
small declarative YAML that diffs cleanly and can be authored remotely without
Xcode; Kevin regenerates with `xcodegen generate` after any `project.yml`
change. The `.xcodeproj` itself is gitignored. If XcodeGen ever becomes a
constraint we can check in the generated project and drop the tool — one-way
door in the safe direction.

`.gitignore` starts with: `*.xcodeproj`, `Generated/`, `build/`, `DerivedData/`,
`fixtures/`, `.DS_Store`, `fastlane/report.xml`, `*.ipa`, `*.dSYM.zip`,
`.env*`, plus the standard Swift/Xcode noise.

## 3. Rust core → Swift packaging

`scripts/build-core.sh` does, in order: resolve the core checkout (sibling >
submodule > `$VAULTPONY_CORE`); `cargo build -p vault-ffi --release --locked`
for `aarch64-apple-ios` and `aarch64-apple-ios-sim`; run
`uniffi-bindgen generate --library … --language swift` to emit
`vault_ffi.swift`, the C header, and the modulemap into `Generated/`; assemble
`VaultFFI.xcframework` with `xcodebuild -create-xcframework` from the two
static libraries plus headers; drop it in `Generated/`. Everything under
`Generated/` is gitignored and rebuilt deterministically (`--locked`, pinned
toolchain from the core's `rust-toolchain.toml`).

Notes that will save debugging later: the generated Swift file and the compiled
library carry matching UniFFI checksums, so the script always regenerates both
together — never mix a stale binding with a fresh library. `panic = "abort"`
in the core's release profile is correct for static linking into an app. No
x86_64 simulator slice unless an Intel Mac shows up in practice; adding one is
a one-line change (`x86_64-apple-ios` + `lipo` the sim slices together).
`IPHONEOS_DEPLOYMENT_TARGET=17.0` is set in `project.yml`; the Rust side does
not care. Prerequisite PR to VaultPonyCore: add the two iOS targets to
`rust-toolchain.toml`'s target list so `rustup` provisions them.

Build order for a clean checkout is: `./scripts/build-core.sh`, then
`xcodegen generate`, then build in Xcode or `xcodebuild`. The Xcode target gets
a pre-build phase that runs `build-core.sh` in incremental mode (cargo makes
this cheap when nothing changed), so day-to-day iteration is just ⌘R.

## 4. The FFI surface we consume

From VaultPonyCore `vault-ffi` as of today — the plan treats this as complete
for parity, since it is exactly what Android ships on:

| Area | Functions |
|---|---|
| Registry | `core_version`, `encryption_schemes`, `hashes`, `filesystems` |
| Create | `create_container(fd, size, passphrase, pim, keyfiles, scheme, prf, filesystem)`, `create_hidden_container(…)` |
| Header ops | `export_header_backup(fd)`, `restore_header_from_file`, `restore_header_from_embedded`, `change_password` |
| Session | `VaultSession.unlock_fd(fd, passphrase, pim, keyfiles, listener)`, `unlock_outer_protected_fd(…)`, `facts`, `list`, `stat`, `read_at`, `write_at`, `create`, `mkdir`, `rename`, `remove`, `truncate`, `flush`, `lock` |
| Progress | `UnlockProgressListener.on_progress(step, total, prf)` |

`CoreBridge/` wraps this in idiomatic Swift: async wrappers that hop off the
main actor (unlock is CPU-bound for seconds — 500k PBKDF2 iterations),
`VaultError` mapped to user-facing localized messages, and a `Vault` façade so
no screen touches the generated types directly. One gap to flag, not assume:
`create_hidden_container` takes no keyfiles today; if Android exposes keyfiles
on hidden-volume creation we match it, otherwise parity is "no keyfiles for
hidden create" on both platforms — verify against the Android
CreateContainerScreen during P3.

## 5. Opening files on iOS — the platform-risk section

This is the one area where iOS is materially harder than Android, so it gets
its own section and its own early gate.

The happy path: `fileImporter`/`UIDocumentPickerViewController` in open-in-place
mode (`asCopy: false`) hands us a security-scoped URL. We call
`startAccessingSecurityScopedResource`, `open(2)` the path `O_RDWR`, hand the
fd to the core, and store a security-scoped bookmark so the vault reappears in
Recents across launches. This works for: files in On My iPhone/iPad, iCloud
Drive (once materialized), and third-party file providers that support
open-in-place.

The sharp edges, and what we do about them. iCloud Drive files can be
dataless (evicted); before opening we check `ubiquitousItemDownloadingStatus`
and trigger `startDownloadingUbiquitousItem`, showing determinate progress —
never hand the core an fd to a dataless file. Some file providers refuse
open-in-place or hand back non-seekable access; on `open(2)` failure or a
provider without the capability we fall back to an explicit, user-visible
copy-in/copy-back flow (copy to app container with `NSFileProtectionComplete`
+ backup exclusion, work there, offer "export back" on lock) — clearly labeled
because copy-back is a divergence from edit-in-place, and no-trace mode
disables the fallback entirely rather than silently copying. Writes through a
file provider's open-in-place fd are coordinated with `NSFileCoordinator`
around the open, and we `flush()` the core session on every
scene-background transition so a provider sync mid-session never sees a
half-written filesystem (the core's FAT/exFAT writers are already
powerloss-safe, which covers the same class of interruption).

P1's gate explicitly includes a device-matrix test of open-in-place across On
My iPhone, iCloud Drive, and at least one third-party provider, because this
is the assumption the whole app stands on.

## 7. Security posture, iOS-specific deltas

THREAT_MODEL-IOS.md (written in P0, kept current at every gate) inherits the
core threat model and adds the shell deltas. The headline items:

Secrets in Swift memory: Swift `String`/`Data` cannot be reliably zeroized
(copy-on-write, bridging). Mitigation matches Android's: keep the foreign-side
lifetime of the passphrase as short as possible — captured from SecureField,
passed across the FFI (where the Rust side wraps it in `Zeroizing`
immediately), reference dropped at once, never logged, never in userInfo,
never in state restoration. The standing pre-release audit of generated glue
for lingering foreign-side copies now covers the Swift bindings too — same
gate as the Kotlin audit in the core's THREAT_MODEL review gates.

Keychain: biometric unlock stores the passphrase (not a derived key — PIM and
keyfiles factor in at unlock time) under
`kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` + `biometryCurrentSet`.
Opt-in per vault, off by default, wiped when the vault is removed from
Recents or when unlock with it fails with wrong-password.

At-rest app data: Recents store and prefs contain bookmarks and settings, no
secrets; still `NSFileProtectionComplete` and excluded from backup (a bookmark
restored to another device is useless but leaks vault filenames). No decrypted
content ever touches disk except the explicit copy-in fallback and explicit
exports, both `NSFileProtectionComplete`, backup-excluded, and cleaned on lock.

Zero network: no networking code, no analytics, no third-party SDKs. iOS has
no user-visible network permission to point at, so the claim is backed by the
open source + a `NSAllowsArbitraryLoads`-absent ATS posture and, post-v1,
possibly a network-extension-free privacy manifest. Privacy Nutrition Label:
"Data Not Collected."

App Store specifics tracked for P7: encryption export compliance
(`ITSAppUsesNonExemptEncryption` true + French declaration + annual
self-classification report), the IDRIX/VeraCrypt trademark notice in the app
and store listing, and the review-guideline framing (container utility, not a
"secret" app — Apple rejects deceit-marketed vault apps; ours is a transparent
open-source utility).

## 8. Phases and gates

Each phase lands as a PR train on `main` behind the gate; the gate is a
demoable, testable state, mirroring how the core's P-gates worked.

**P0 — Reset and walking skeleton.** Salvage check: confirm the fixture corpus
is regenerable from VaultPonyCore `tools/gen-fixtures` (or copy the five `.vc`
fixtures out of the old monorepo into safekeeping first). Wipe `~/Apps/VaultPony`
(old contents to `_to_delete/`, Kevin empties it), `git init`, repo-local
`norsehorse-dev` identity before the first commit, seed with LICENSE, NOTICE,
README, PLAN.md, THREAT_MODEL-IOS.md skeleton, `.gitignore`, `project.yml`,
submodule. Core PR: add iOS targets to `rust-toolchain.toml`.
`build-core.sh` produces the xcframework; the app builds and shows
`core_version()` on an About placeholder. CI green on a macOS runner.
Gate: ⌘R on simulator and on Kevin's iPhone shows the core version string.
Publishing the GitHub repo happens here — after an explicit go-ahead on
identity and visibility.

**P1 — Unlock, browse, read.** FdOpener with the full section-5 behavior
(minus copy-in fallback), Home + Recents with bookmarks, UnlockView with
password/PIM/keyfiles and progress, BrowserView read-only, ViewerView for
text/images/PDF, lock/auto-lock, SessionRegistry, PrivacyShield.
Gate: every fixture in the corpus unlocks and lists correctly through XCTest
on simulator; open-in-place verified on device across On My iPhone, iCloud
Drive, and one third-party provider; wrong-password UX matches the
deliberately-coarse error contract.

**P2 — Read-write.** Browser gains mkdir/rename/delete/import/export, viewer
stays read-only, write path wired (`write_at`, `create`, `truncate`, `flush`),
flush-on-background, copy-in/copy-back fallback flow.
Gate: roundtrip XCTests (write on iOS, verify bytes through a fresh unlock);
cross-check a container edited on iOS opens clean in VaultPonyAndroid and the
CLI; powerloss-adjacent test — kill the app mid-write, container still mounts.

**P3 — Create.** CreateContainerView, plain and hidden flows,
outer-protected unlock mode surfaced in UnlockView's advanced options,
VaultCreatedView.
Gate: iOS-created containers (every scheme × PRF × FS the registry offers)
unlock via the CLI and match the fixture matrix expectations; hidden-volume
outer-write protection demonstrated (write to outer that would clobber hidden
→ `HiddenVolumeProtected`, volume latches read-only).

**P4 — Custody.** ChangePasswordView, RecoveryView (header backup export /
restore from file / restore embedded), keyfile management polish.
Gate: header damaged deliberately → restored from backup → unlocks; password
changed on iOS → old fails, new works, on Android too.

**P5 — Platform trust features.** Biometric unlock (Keychain per section 7),
no-trace mode end-to-end, Settings complete, backup-exclusion and
file-protection audit.
Gate: Face ID unlock round-trips; biometry re-enrollment invalidates stored
passphrases; no-trace verified with a filesystem sweep after a full session.

**P6 — Polish and parity closeout.** All six localizations, iPad layouts
(split view: browser/viewer side-by-side), Dynamic Type + VoiceOver pass,
in-app language switching decision executed, empty/error states, app icon.
Gate: parity checklist against the Android README feature list, every row
checked on device in two languages.

**P7 — Release.** fastlane (match/gym/pilot mirroring the Android lane
structure), TestFlight, export compliance, store listing, privacy label,
screenshots, THREAT_MODEL-IOS.md review gates closed including the Swift glue
audit.
Gate: TestFlight build in external testers' hands.

**P8 — post-v1.** File Provider extension (vault in Files app system-wide):
its own design doc first — process isolation for key material, the extension's
memory ceiling vs PBKDF2, XPC session brokering vs re-unlock, and whether the
core needs a no-cache streaming mode. Also parked here: Handoff/state
restoration (likely permanently out — restoring into an unlocked state is a
threat-model violation), and desktop.

## 9. Testing strategy

The fixture corpus is the spec, same as everywhere else in the project.
`fetch-fixtures.sh` materializes it (regenerating via the core's tools, or
copying from a local cache) into `fixtures/` (gitignored); VaultPonyTests skip
with a loud message when the corpus is absent, exactly like the core's
`SKIP: fixture corpus not present` convention. The XCTest suite mirrors the
Rust FFI tests through the Swift bindings — unlock/browse/read/lock, wrong
password, facts — then adds the iOS-only layers: FdOpener behaviors (including
a dataless-file simulation), VaultStore bookmark staleness, Keychain
store/invalidate (on-device only), auto-lock timing, and the P2 write
roundtrips. UI tests stay minimal: one happy-path flow per phase, because
simulator UI tests are the flakiest thing we'll own.

CI on `macos-15` (or current): checkout with submodule, rustup with the
pinned toolchain + iOS targets, cargo cache, `build-core.sh`,
`xcodegen generate`, `xcodebuild test` on an iPhone simulator, fixtures
regenerated in-job if the generator is cheap enough, otherwise unlock tests
marked skip-in-CI and the fixture suite runs locally per phase gate (decide in
P1 based on generator runtime).
